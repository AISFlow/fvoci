# 표준 구현 재사용

정책·권한·모델은 루트 AGENTS.md를 따른다. 이 스킬은 구현 선택 절차이지 특정 crate의 설치 승인이나
새 기능 목록이 아니다. 무관한 CRUD에 모든 후보를 조사하지 않고, 기존 차단 수정·담당 작업을 보존한다.

## 입력

고정 코드 SHA·변경 경계, 원본/클라이언트 계약, 적용 명세와 보안 프로파일, 현재 의존성/feature,
호출자의 제품 정책, 기존 회귀와 허용 수정 경로. 원본 계약은 [source-contract](../fvoci-source-contract/SKILL.md)로 좁힌다.

## 절차

1. **범위를 고정한다.** 명세 버전·필수/선택 기능·errata·보안 BCP와 실제 클라이언트 사용 범위를
   확인한다. 모든 RFC가 같은 성격이나 강제력을 갖는다고 보지 않는다. OIDC·MCP·문서 형식도 각 공식
   명세로 다루며 최신 SDK 채택을 프로토콜/제품 기능 확대와 혼동하지 않는다.
2. **기존 구현을 먼저 찾는다.** 현재 적합한 의존성 → 공식 SDK/유지보수되는 Rust 구현 → 얇은 제품
   adapter 순서로 비교한다. 암호 primitive만 재사용하면서 JWT/OIDC 전체를 위임했다고 하지 않는다.
   [후보와 검증 경계](references/candidates.md)는 관련 절만 읽는 조사 시작점이며 일괄 설치 목록이 아니다.
   복구 archive의 tar header·entry 검사는 유지보수되는 parser에 맡기고 경로·타입 허용 정책만 제품에서 둔다.
3. **책임을 분리한다.** 라이브러리는 파싱·검증·직렬화·프로토콜 수명주기를, FVOCI는 계정 연결·현재
   권한·세션 철회·DB 원자성·저장/재시도 정책을 맡는다. 검증 전 입력을 검증된 identity와 혼용하지
   않는다. [db-security](../fvoci-db-security/SKILL.md)의 현재 인가·경합 검사는 SDK로 대체되지 않는다.
4. **실제 설정과 비용을 확인한다.** 공식 출처·선정 버전·라이선스·유지보수/보안 권고, 현재 toolchain·
   Tokio/HTTP/TLS 호환, 최소 feature와 전이 의존성을 확인한다. 기본 redirect/proxy/외부 schema 조회,
   입력·응답·시간·메모리 제한, 취소/종료 동작이 기존 보장을 약화하지 않아야 한다. 필요한 경우 지원되는
   custom client를 연결한다. README의 준수 주장·인기·Rust 사용·권고 부재를 감사 완료로 해석하지 않는다.
5. **한 경계만 교체한다.** manifest/lockfile의 단독 소유권을 코디네이터에게서 받고 배포 버전을 기존 정책과 lockfile로
   고정한다. 무관한 upgrade나 moving-main 의존성을 함께 넣지 않는다. 먼저 작은 adapter와 회귀로
   연결한 뒤 정상 호출을 전환한다. 보안 검증 실패를 기존 느슨한 구현으로 재시도하는 fallback은 금지한다.
6. **비교하고 중복을 제거한다.** 공식 벡터와 허용/거부 입력, 실제 client/server, 현재 제품의 DB·UI·
   복구 경계를 [fast-verify](../fvoci-fast-verify/SKILL.md)로 검사한다. 차등 비교는 격리 fixture에서 하며
   로그인·메일·DB 쓰기를 제품에서 이중 실행하지 않는다. 기존 결과가 명세와 다르면 알려진 결함을
   복제하지 않는다. 전환이 검증된 구간의 자체 parser/validator·중복 정상 경로는 제거한다.
   SDK의 출력 표현 차이만으로 배제하지 않는다. 실제 소비자와 데이터 의미를 검사하고, 보정 코드는 새
   구현에서도 필요한 보장을 설명할 수 있을 때만 유지한다. 명확한 결함 수정·의미 보존 정규화는 관련 회귀로 수락한다.

## 유지할 안전 경계

라이브러리를 추가해도 issuer/subject 매핑, replay 방지, lease/fence, RLS, 영속 commit, 복구 키 보관은
자동 완성되지 않는다. bool 검증만 받아 필요한 검증된 claim·step을 잃지 않게 한다. 암호 알고리즘·
constant-time 처리는 검증된 구현을 우선하고, 손으로 쓴 비교 루프의 timing을 컴파일러와 무관하게 보장하지 않는다.

기존 작은 구현이 더 적합하면 구체적인 공백·비용·검증 근거를 남겨 유지할 수 있다. 이미 발견한 결함을
방치하거나 매 PR마다 비교를 다시 시작할 구실은 아니다. 긴 교체가 긴급 보안 수정을 막으면 최소 수정부터
수락하고 교체는 별도 PR로 진행한다. 라이브러리를 쓰기 위해 새 서비스·바이너리·범용 framework를 만들지 않는다.

## 결과와 수락

기존 PR/task에 적용 명세·선정 버전/feature·맡긴 책임·남긴 제품 정책·제거한 자체 구현·실제 검증 SHA와
미검증 범위를 짧게 남긴다. build/크기/지연은 필요한 대표 조건에서 측정한 것만 보고한다. crate 추가나
코드 줄 수 감소가 아니라 동일한 제품 보장을 더 적은 직접 구현으로 유지하는 것이 수락 기준이다.
별도 평가 플랫폼·중복 backlog·프로토콜 버전 자동 업그레이드는 만들지 않는다.
