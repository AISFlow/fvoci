# Helper inputs and boundaries

Run with Bun using the script's absolute path. `inspect [--profile FILE]` is read-only. It returns context references and fleet projections, including all worker-list pages; it never copies command environments or transcript bodies. Re-read HANDOFF/state for the actual next action and current approvals. A locator is a pointer, not authorization or a replacement task ledger.

The private JSON profile follows the exact `Profile` type and `loadProfile` keys in [coordinator.ts](../scripts/coordinator.ts); version is 2. Paths are absolute and must exist. `repo` is the filesystem Git source checkout, not an Orca repository selector; `parent` is the coordinator checkout. Context reads both worktree receipts, resolves the parent repo ID through `repo show --repo id:<repoId>`, and compares their Git common directories with the registered repository. Missing, conflicting or ambiguous mapping is refused before mutation; creation uses that verified `id:` selector without another-project fallback. `parentId` and `parentInstance` must match Orca's current parent receipt. `controller`, `worker` and the optional `reviewer` (absent: reviewers use `worker`) contain exactly `adapter`, `model`, `effort`, `tier`, `banner`. Set them from the current user instruction, not the historical launcher. `adapter` names the execution adapter explicitly: `codex` or `claude`. Any other value is refused; no adapter is inferred from a model, banner, checkout or executable name, and other providers require a separately reviewed adapter, not a profile rename. `tier` is `default` (Fast off) for workers and reviewers. Only a `codex` controller may explicitly select `fast`; its default remains `default`. The `claude` adapter accepts only `default` in every role and has no Fast tier. Unknown tiers, including `ultrafast`, are refused. A `codex` entry keeps `model` equal to the lowercased `banner` its TUI shows. A `claude` entry uses the full provider model ID its session transcripts record, because an alias cannot be confirmed, and its `banner` is a display label that is never used as evidence. The top-level `codex` executable path is required only when `worker` or `reviewer` uses `codex`. `concurrency` is a positive integer, or null when the user set no fixed worker cap; the heavy-command entrypoint still governs load. Version 1 locators predate explicit adapters and are refused: rewrite them from current verified receipts and user model choices instead of adding a guessed adapter. Do not store credentials, URLs, hosts, environment dumps, current task outcomes or copied transcripts here. On another machine, supply a verified local profile rather than guessing paths or IDs.

`launch --request FILE [--profile FILE]` is a mutating controller operation: use only after an explicit task assignment. Its private JSON request contains exactly `role` (`author` or `reviewer`), `unit`, `branch`, `sha` (40 lowercase hex), `worktree` (absolute), `prompt` (unit instruction path), `report` (future report path), `spec` (self-contained Orca Task spec), `name` (new worktree display name), `terminal` (null or explicitly selected existing agent handle). Prompt and report are inside this profile's scratch/unit directory; common prompts must exist. The Task spec must describe target, change, constraints, ownership and observable acceptance; the controller owns its correctness. The spec must contain the request branch as well as the combined prompt path; the branch is the submission target, not a request to rename the Orca checkout. Unit-specific no-push instructions override a generic branch convention. The helper combines common and unit instructions into `dispatch-prompt.md` before launch. In the spec, point to that combined file; it must exist before injecting the spec. The role's profile entry selects the adapter.

Launch validates the source commit object and clean source checkout, exact clean target base, current Run/coordinator and both directions of parent lineage. It rejects existing checkouts with missing/wrong lineage instead of silently adopting another session. New checkouts pass an explicit parent and are verified again, and both lineage directions are rechecked immediately before the authoritative start. These steps are common to both adapters; the agent start differs. Both adapters require a local POSIX host.

With `codex`, a newly created checkout must expose exactly one startup shell; missing or ambiguous inventory stops with residual resources preserved, rather than creating a second terminal. The sole connected shell must match the intended worktree and expose, in `terminal read`, a running shell whose last line is a prompt, with no agent identity and none of the TUI glyphs or input hints observed on real agent screens (box drawing, status and spinner marks, agent prompt characters). Provider names alone are not markers, because they occur in prompt cwd paths. Do not wait for `tui-idle` on a plain shell: that condition belongs to an agent TUI. Replace the positively observed shell with `exec`, then wait for the agent TUI and verify its banner. An existing agent requires an explicit request terminal, a completed succeeded/failed Dispatch retained in this Run, and a matching TUI banner. An active or unknown prior agent is refused. The controller must also verify that the terminal has not since been assigned to another session or Run. It never opens a second agent next to an automatic startup shell. New existing-checkout terminals are created only when the checkout has no terminals. Posix argv quoting is used solely for Orca's documented command-text boundary; CLI and Git calls use argv arrays. Its launch argv uses unrestricted approval and runtime access, matching the existing entrypoints; this is not a security sandbox. Controller and worker TUI model/effort/Fast banners are verified. Only a Fast token immediately after the effort denotes Fast; a later ultrafast availability hint does not. An update menu is refused for operator inspection, without automatic UI input.

For `codex`, the current terminal receipt fields are `result.send.handle` and `result.send.accepted` for input acceptance, and `result.wait.handle`, `condition`, `satisfied`, `status` for readiness. The helper's `cli()` returns `result`, so it reads `send` and `wait` beneath that object, never flat acceptance/readiness fields. Require the selected handle, accepted input, and a satisfied `tui-idle` wait on a running TUI before Task injection. A missing, wrong or partial receipt stops with the attempt marker and residual resources preserved; an accepted send alone does not prove a supervised start. Do not resend, increase a timeout, or substitute another terminal to repair uncertainty.

With `claude`, Orca's own launcher starts the agent through exactly one `orchestration worker-start --worktree path:<verified child> --agent claude --model <model> --effort <effort>` call in this Run. The request terminal must be null: Orca does not combine `--model` or `--effort` with `--terminal`, so reuse has no model-controlled route. An existing checkout must have no terminals. A new checkout's startup terminals must be plain terminals of that worktree with no agent identity; their handles are recorded in `startup-terminals.json` in the unit directory before the start and are never sent input, waited on or closed. Success requires exit 0 with a `ready` receipt in the same Run, string Task and Dispatch IDs, a created agent terminal that is not a recorded startup terminal with accepted Dispatch input, and `launch.requested` and `launch.effective` both equal to the profile's agent, model and effort. A non-zero exit, partial receipt or any difference is refused; `launch.once`, the checkout, startup terminals and any created terminal stay in place, and the error names the preserved startup terminals. There is no retry, substitute terminal or cleanup.

The helper creates a private per-unit `launch.once` before the first mutation and records no automatic retry. Preserve that marker and all residual resources on a failed stage or unknown receipt; inspect them with Orca recovery guidance. A controller must resolve the previous attempt before explicitly permitting a new one. Never delete the marker merely to make a failed command pass. Success requires the agent terminal in a ready worker-start receipt plus Task and Dispatch IDs; a partial result is unknown, not success. Existing agent reuse must follow Orca's proven settlement/reuse contract first.

`confirm --dispatch ID [--role author|reviewer] [--profile FILE]` is read-only and applies to `claude` launches, because a launch receipt does not prove the model that actually answered. It reads `worker-show` for that Dispatch, requires this Run and repository, and requires the recorded effective launch to equal the role's profile entry. It then reads the installed Claude Code session transcripts for the Dispatch's worktree, `~/.claude/projects/<launch cwd with "/" replaced by "-">/<session>.jsonl`. That mapping was observed on the installed CLI only for paths made of letters, digits, `/` and `-`; other paths are refused. Only top-level session files whose first recorded cwd is the worktree and whose plain-text user prompt carries the Dispatch ID count; subagent files, older sessions and tool output naming the Dispatch do not. Every assistant turn must record `message.model` and `effort` equal to the profile entry. Without an assistant turn yet, it returns `PENDING` and does not wait or sleep; any mismatch fails. It prints counts and the verdict, never transcript text.

Controller evidence follows its adapter. For `codex`, it is the controller screen banner with the exact model, effort and configured tier: `default` requires no Fast token, and `fast` requires the literal `fast` token immediately after effort, before the status separator or end of line. A later availability hint does not establish Fast, and Ultrafast or unknown tier tokens are refused. For `claude`, the coordinator terminal must carry the `claude` agent identity. The installed Claude Code screen did not show the model or effort, and typed composer text could imitate a label, so screen text is not evidence; the evidence is the controller's own session transcript under the parent checkout's transcript directory. When the caller is the coordinator, that is the session named by its Claude Code session environment; otherwise exactly one candidate session must exist. Its latest assistant turn must record the profile model and effort. Missing evidence, several candidates or a mismatch refuse.

`wait --out FILE [--profile FILE]` performs one wait and writes the complete private receipt at FILE, which must not exist. It uses a per-Run exclusive local waiter guard and Orca's server waiter exclusion. Do not run it alongside an existing legacy waiter, even if that waiter did not create the local guard. A crash leaves the guard for explicit inspection; do not reclaim it based on PID absence alone. Timeouts are checkpoints. The next owner decides whether another wait is needed.

`process --decisions FILE [--profile FILE]` consumes the current delivery once and shares the waiter's exclusive guard. FILE is a private JSON object `{deliveryId, messages}`; `messages` maps every current message ID to exactly one decision. A question decision is `{answer: "..."}`; every other decision is `{handled: true}`. `handled` attests that the controller processed the full body, checked active Task/Dispatch for completion, and performed required next-owner actions under Orca's guide. This helper performs no acceptance or lifecycle decision. It validates the complete decision set before replying by original ID, then acknowledges exactly that delivery. It returns the full next batch from the ack, without dropping new arrivals. If reply/ack fails, preserve the receipt and do not replay automatically. A reply may already have succeeded: removing a guard and replaying the batch can send the same answer twice. Reconcile Orca receipts before manual recovery.

Both wait and process require the current caller's Orca terminal environment to equal the locator coordinator. This is an environment guard against accidental misuse, not authentication or protection against a caller forging environment values. Orca remains the authority. A new controller session must complete the Run binding below, update the private locator from verified receipts, and inspect again. `inspect` works from other cwd without changing bindings, and it refuses a locator whose coordinator is not the Run's bound coordinator. No helper changes live launchers, current wait processes, global configuration, repository policies or agent model settings.

Run binding. A new controller session binds the existing Run and never creates a replacement Run. Preconditions: the previous coordinator has stopped mutating; no inbox waiter is running, proven by a host process count of zero live `orchestration check --wait` calls (an unknown count stops); the current unacknowledged delivery ID and its message IDs are recorded. From the new coordinator's own Orca terminal, run `orchestration run-use --id <run> --json` without `--from`. `--from` selects the calling identity rather than nominating a new coordinator, so `run-use --from <previous handle>` can report success while the binding stays unchanged; that is not a takeover. Afterwards `orchestration run-show --id <run>` must show `coordinator_handle` equal to the new terminal's handle and a higher `consumer_generation` than before, and `orchestration run-current` in the new terminal must return the Run. A no-op, refusal or unknown receipt stops: report the exact receipt, and do not guess a retry, create a new Run or bind another terminal. Pending mail moves to a new delivery ID after rebinding, so reconcile the first check with the recorded batch by message ID before handling or acknowledging it. Update the locator's `coordinator` only after these receipts verify, then rerun `inspect`. A legacy adopted Run uses Orca's separate legacy takeover reference instead.

`legacy.ts worker UNIT DRAFT_BRANCH SHA40`, `legacy.ts review REVIEW_ID SHA40 ABSOLUTE_REPORT DRAFT_BRANCH`, and `legacy.ts wait ABSOLUTE_NEW_RECEIPT` preserve the existing entrypoint interfaces. An optional trailing `--profile FILE` selects a verified private locator. Worker uses the `worker` entry and review uses the `reviewer` entry (default `worker`). Before any mutation, the guard at the start of [legacy.ts](../scripts/legacy.ts) requires that entry to name a supported adapter that satisfies its constraints (`codex`: model matching its banner and Fast off; `claude`: full model ID and tier `default`), and an inherited effort override that differs from the entry is refused. A review-model exception is a `reviewer` entry on a supported adapter, not a separate route. They copy `scratch/prompts/<unit>.md` into the unit prompt, select the existing author/reviewer common instructions, write a mode-0600 request, then invoke the same launch helper. Common attribution is left intact and must request the actual worker session, never the caller session. Worktree names beside the parent checkout keep the existing compatibility names; a `claude` reviewer uses its own prefix so a checkout left by the other adapter is never adopted. Reports stay inside scratch/unit. Existing request, report, marker or differing prompt is refused; existing terminals require the explicit reuse route, never first-terminal selection. Missing commits are refused without fetch. The wait adapter writes `{ok:true,result:<complete batch>}` once with no ack or loop; the controller handles every message and the next batch returned by process.
