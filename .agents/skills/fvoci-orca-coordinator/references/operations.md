# Helper inputs and boundaries

Run with Bun using the script's absolute path. `inspect [--profile FILE]` is read-only. It returns context references and fleet projections, including all worker-list pages; it never copies command environments or transcript bodies. Re-read HANDOFF/state for the actual next action and current approvals. A locator is a pointer, not authorization or a replacement task ledger.

The private JSON profile follows the exact `Profile` type and `loadProfile` keys in [coordinator.ts](../scripts/coordinator.ts); version is 1. Paths are absolute and must exist. `repo` is the filesystem Git source checkout, not an Orca repository selector; `parent` is the coordinator checkout. Context reads both worktree receipts, resolves the parent repo ID through `repo show --repo id:<repoId>`, and compares their Git common directories with the registered repository. Missing, conflicting or ambiguous mapping is refused before mutation; creation uses that verified `id:` selector without another-project fallback. `parentId` and `parentInstance` must match Orca's current parent receipt. `controller` and `worker` contain exactly `model`, `effort`, `tier`, `banner`. Set them from the current user instruction, not the historical launcher. The bundled execution adapter supports only its current CLI protocol and tier `default`; inspect its launch argv and the stricter compatibility guard in [legacy.ts](../scripts/legacy.ts) before choosing local executables and models. Other providers or tiers require a separately reviewed adapter, not a profile rename. Do not store credentials, URLs, hosts, environment dumps, current task outcomes or copied transcripts here. On another machine, supply a verified local profile rather than guessing paths or IDs.

`launch --request FILE [--profile FILE]` is a mutating controller operation: use only after an explicit task assignment. Its private JSON request contains exactly `role` (`author` or `reviewer`), `unit`, `branch`, `sha` (40 lowercase hex), `worktree` (absolute), `prompt` (unit instruction path), `report` (future report path), `spec` (self-contained Orca Task spec), `name` (new worktree display name), `terminal` (null or explicitly selected existing agent handle). Prompt and report are inside this profile's scratch/unit directory; common prompts must exist. The Task spec must describe target, change, constraints, ownership and observable acceptance; the controller owns its correctness. The spec must contain the request branch as well as the combined prompt path; the branch is the submission target, not a request to rename the Orca checkout. Unit-specific no-push instructions override a generic branch convention. The helper combines common and unit instructions into `dispatch-prompt.md` before launch. In the spec, point to that combined file; it must exist before injecting the spec.

Launch validates the source commit object and clean source checkout, exact clean target base, current Run/coordinator and both directions of parent lineage. It rejects existing checkouts with missing/wrong lineage instead of silently adopting another session. New checkouts pass an explicit parent and are verified again. A newly created checkout must expose exactly one startup shell; missing or ambiguous inventory stops with residual resources preserved, rather than creating a second terminal. The sole connected shell must match the intended worktree and expose a running shell prompt in `terminal read`, with no agent identity or agent screen. Do not wait for `tui-idle` on a plain shell: that condition belongs to an agent TUI. Replace the positively observed shell with `exec`, then wait for the agent TUI and verify its banner. An existing agent requires an explicit request terminal, a completed succeeded/failed Dispatch retained in this Run, and a matching TUI banner. An active or unknown prior agent is refused. The controller must also verify that the terminal has not since been assigned to another session or Run. It never opens a second agent next to an automatic startup shell. New existing-checkout terminals are created only when the checkout has no terminals. Posix argv quoting is used solely for Orca's documented command-text boundary; CLI and Git calls use argv arrays. This adapter requires a local POSIX host. Its launch argv uses unrestricted approval and runtime access, matching the existing entrypoints; this is not a security sandbox. Controller and worker TUI model/effort/Fast banners are verified. Only a Fast token immediately after the effort denotes Fast; a later ultrafast availability hint does not. An update menu is refused for operator inspection, without automatic UI input.

The current terminal receipt fields are `result.send.handle` and `result.send.accepted` for input acceptance, and `result.wait.handle`, `condition`, `satisfied`, `status` for readiness. The helper's `cli()` returns `result`, so it reads `send` and `wait` beneath that object, never flat acceptance/readiness fields. Require the selected handle, accepted input, and a satisfied `tui-idle` wait on a running TUI before Task injection. A missing, wrong or partial receipt stops with the attempt marker and residual resources preserved; an accepted send alone does not prove a supervised start. Do not resend, increase a timeout, or substitute another terminal to repair uncertainty.

The helper creates a private per-unit `launch.once` before the first mutation and records no automatic retry. Preserve that marker and all residual resources on a failed stage or unknown receipt; inspect them with Orca recovery guidance. A controller must resolve the previous attempt before explicitly permitting a new one. Never delete the marker merely to make a failed command pass. Success requires the same terminal in a ready worker-start receipt plus Task and Dispatch IDs; a partial result is unknown, not success. Existing agent reuse must follow Orca's proven settlement/reuse contract first.

`wait --out FILE [--profile FILE]` performs one wait and writes the complete private receipt at FILE, which must not exist. It uses a per-Run exclusive local waiter guard and Orca's server waiter exclusion. Do not run it alongside an existing legacy waiter, even if that waiter did not create the local guard. A crash leaves the guard for explicit inspection; do not reclaim it based on PID absence alone. Timeouts are checkpoints. The next owner decides whether another wait is needed.

`process --decisions FILE [--profile FILE]` consumes the current delivery once and shares the waiter's exclusive guard. FILE is a private JSON object `{deliveryId, messages}`; `messages` maps every current message ID to exactly one decision. A question decision is `{answer: "..."}`; every other decision is `{handled: true}`. `handled` attests that the controller processed the full body, checked active Task/Dispatch for completion, and performed required next-owner actions under Orca's guide. This helper performs no acceptance or lifecycle decision. It validates the complete decision set before replying by original ID, then acknowledges exactly that delivery. It returns the full next batch from the ack, without dropping new arrivals. If reply/ack fails, preserve the receipt and do not replay automatically. A reply may already have succeeded: removing a guard and replaying the batch can send the same answer twice. Reconcile Orca receipts before manual recovery.

Both wait and process require the current caller's Orca terminal environment to equal the locator coordinator. This is an environment guard against accidental misuse, not authentication or protection against a caller forging environment values. Orca remains the authority. A new controller session must complete the documented Orca takeover separately, update the private locator from verified receipts, and inspect again. `inspect` works from other cwd without changing bindings. No helper changes live launchers, current wait processes, global configuration, repository policies or agent model settings.

`legacy.ts worker UNIT DRAFT_BRANCH SHA40`, `legacy.ts review REVIEW_ID SHA40 ABSOLUTE_REPORT DRAFT_BRANCH`, and `legacy.ts wait ABSOLUTE_NEW_RECEIPT` preserve the existing entrypoint interfaces. An optional trailing `--profile FILE` selects a verified private locator. Worker/review require the exact compatibility model, effort and Fast-off settings enforced at the start of [legacy.ts](../scripts/legacy.ts); other selections are refused. They copy `scratch/prompts/<unit>.md` into the unit prompt, select the existing author/reviewer common instructions, write a mode-0600 request, then invoke the same launch helper. Common attribution is left intact and must request the actual worker session, never the caller session. Worktree names remain the adapter's existing compatibility names beside the parent checkout. Reports stay inside scratch/unit. Existing request, report, marker or differing prompt is refused; existing terminals require the explicit reuse route, never first-terminal selection. Missing commits are refused without fetch. The reviewer-provider exception remains a separate controller route. The wait adapter writes `{ok:true,result:<complete batch>}` once with no ack or loop; the controller handles every message and the next batch returned by process.
